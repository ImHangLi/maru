# Quick add: fill the add screen with almost no typing, 2026-10-11

The owner's request: "Photo input matters. Typing is tiring. A user types for a while and then gives up. Look for mature solutions that we can put in directly, for example voice input or other ways."

The answer: build a live label scan with Apple's VisionKit data scanner first. The user points the camera at the bottle and taps the name on the label. It runs on the device, on every iPhone that Maru supports, with no network and no cost. The on-device language model is the second step, because only a part of the iPhones have it.

Each claim has a tag. **Verified** means that a primary source says it or a request showed it on 2026-10-11, and the link follows. **Inferred** means a conclusion from the sources that no test confirmed. No code ran on a device for this note, and no build ran.

## 1. What the add screen needs today

Source: `App/Editor/ItemEditorView.swift`, `App/Editor/ItemDraft.swift`.

| Field | Control today | Typing |
|---|---|---|
| Name (necessary) | Text field | Yes. This is the main cost |
| Type | Segmented control, starts on Supplement (D032) | None |
| Form | Menu of six forms, starts on Capsule (D032) | None |
| Color | Menu, starts on the first free color (D021) | None |
| Amount (optional) | One free text field, "For example 1000 IU" | Yes, if the user wants it |
| Reminder times and days | Time wheel and a list of days | None |
| Note | Menu, free text only for "My own note" | Seldom |

So the typing is the name, and sometimes the amount. A quick add must fill the name. The form and the amount are a bonus. The schedule is not on a label in a form that Maru can use, and spec 2.1 forbids a default time.

Maru supports iOS 17 and later (`project.yml`). **Verified.**

## 3. The facts behind each option

### 3.1 Text recognition on the device

- `DataScannerViewController` scans the live camera video for text and machine-readable codes. It is in iOS 16 and later. **Verified** ([Apple docs](https://developer.apple.com/documentation/visionkit/datascannerviewcontroller)).
- The device must have the A12 Bionic chip or later. The app must check `isSupported` and `isAvailable` before it shows the scanner. **Verified** ([isSupported](https://developer.apple.com/documentation/visionkit/datascannerviewcontroller/issupported)).
- The scanner needs the camera permission and the `NSCameraUsageDescription` text. **Verified** (the same page).
- The scanner highlights each item that it finds, and the app gets the text of the item that the user taps (`dataScanner(_:didTapOn:)`). It can track several items at one time, and it can find text and barcodes in the same session. **Verified** (the same page, initializer parameters `recognizesMultipleItems`, `isHighlightingEnabled`, `isGuidanceEnabled`).
- Every iPhone that runs iOS 17 has the A12 chip or later. **Inferred** from Apple's device list for iOS 17. I did not open that list for this note.
- `RecognizeTextRequest` is the newer Swift API for a still image. It is in iOS 18 and later. `VNRecognizeTextRequest` is the older API, in iOS 13 and later. **Verified** ([RecognizeTextRequest](https://developer.apple.com/documentation/vision/recognizetextrequest), [VNRecognizeTextRequest](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)).
- `RecognizeDocumentsRequest` reads the structure of a document: paragraphs, lists, tables, and barcodes. Apple names "nutritional labels" as an example. It is in iOS 26 and later. **Verified** ([Apple docs](https://developer.apple.com/documentation/vision/recognizedocumentsrequest)). This request can read a "Supplement Facts" table. **Inferred.**
- Live Text in a photo (`ImageAnalyzer` with `ImageAnalysisInteraction`) lets the user select text in a still image. It is in iOS 16 and later. **Verified** ([Apple docs](https://developer.apple.com/documentation/visionkit/imageanalyzer)). The user must select, copy, and paste. That is more steps than one tap in the live scanner. **Inferred.**
- Languages: both APIs give the list at run time (`supportedTextRecognitionLanguages`, `supportedRecognitionLanguages`). Apple's pages do not print the list. English is in the list. **Inferred.** See section 8.
- Curved bottles: Apple gives no accuracy number. A live scanner lets the user turn the bottle until the name is flat to the camera, and a still photo does not. **Inferred.** Only a test on a real iPhone can answer this.

What good apps do: Apple Health shows a list of possible matches after the camera reads the label, and the user picks one ([Tom's Guide](https://www.tomsguide.com/how-to/how-to-set-up-medications-on-your-iphone)). The pattern is always the same: the scan proposes, and the user confirms.

### 3.2 Structured extraction on the device: Foundation Models against a rule parser

Foundation Models:

- The framework is in iOS 26 and later. It gives access to the on-device model of Apple Intelligence. **Verified** ([Apple docs](https://developer.apple.com/documentation/foundationmodels)).
- Guided generation: the `@Generable` macro makes the model return a Swift type, for example a struct with `name`, `form`, and `strength`. **Verified** (the same page).
- Apple lists "entity extraction" as a task that the on-device model does well. **Verified** (the same page).
- Devices: Apple Intelligence runs on iPhone 15 Pro, iPhone 15 Pro Max, iPhone 16 models or later, and iPhone Air. **Verified** ([Apple support](https://support.apple.com/en-us/121115)).
- The model needs up to 8 GB of storage on most iPhones, and up to 14 GB on iPhone 17 Pro, iPhone 17 Pro Max, and iPhone Air. **Verified** (the same page).
- Apple Intelligence does not work on devices bought in China mainland, or when the user is in China mainland with an Apple Account of that region. **Verified** (the same page).
- Languages: English, Danish, Dutch, French, German, Italian, Norwegian, Portuguese, Spanish, Swedish, Turkish, Vietnamese, Chinese (simplified), Chinese (traditional), Japanese, and Korean. **Verified** (the same page).
- A device without the model: `SystemLanguageModel.default.availability` returns `unavailable` with a reason. The reasons are `deviceNotEligible`, `appleIntelligenceNotEnabled`, and `modelNotReady`. Apple tells the app to show an alternative interface. **Verified** ([SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel)).
- Limit: the on-device model has a context window of 4096 tokens for one session. One token is about three to four characters of English. **Verified** ([Managing the context window](https://developer.apple.com/documentation/foundationmodels/managing-the-context-window)). The text of one label fits. **Inferred.**
- Apple changes the model in OS updates. There are three versions now: 26.0 to 26.3, 26.4, and 27.0. A prompt can behave differently on each. **Verified** (SystemLanguageModel page).
- iOS 27 adds images in a prompt (`Attachment`). Apple recommends guided generation with it, and a crop to the region of interest before the call. **Verified** ([Analyzing images with multimodal prompting](https://developer.apple.com/documentation/foundationmodels/analyzing-images-with-multimodal-prompting), [Attachment](https://developer.apple.com/documentation/foundationmodels/attachment)).
- iOS 27 also adds `OCRTool` and `BarcodeReaderTool` in Vision, which a model session can call. `OCRTool` is not available in the Simulator. **Verified** ([OCRTool](https://developer.apple.com/documentation/vision/ocrtool), [BarcodeReaderTool](https://developer.apple.com/documentation/vision/barcodereadertool)).
- Is this use allowed? Apple's acceptable use requirements forbid a use that "provides inaccurate or dangerous outputs, or makes decisions without human supervision that have a material impact on individual rights, in high-risk domains, including in employment, medical, legal, or finance." **Verified** ([Apple](https://developer.apple.com/apple-intelligence/acceptable-use-requirements-for-the-foundation-models-framework/)). A copy of label text into a draft that the user checks is supervised and makes no decision. So the use looks allowed. **Inferred.** Apple did not confirm it.
- Private Cloud Compute (the server model of Apple) is in iOS 27. It needs the network, a managed entitlement from Apple, and it has a daily request limit for each user. **Verified** ([Apple docs](https://developer.apple.com/documentation/foundationmodels/adding-server-side-intelligence-with-private-cloud-compute)). Maru must not use it, because it is a network request with health data.

How many users have the model: 79% of all iPhones and 86% of iPhones from the last four years run iOS 26 (Apple, measured on 2026-06-07). **Verified** ([Apple](https://developer.apple.com/support/app-store/)). Apple does not publish the share of iPhones with Apple Intelligence. iPhone 15, iPhone 15 Plus, and all older models do not have it, and Maru supports them back to the iPhone XS. So a large part of the users gets the fallback. **Inferred.**

The comparison:

| Point | Rule parser | Foundation Models |
|---|---|---|
| Devices | Every iPhone that Maru supports | Only iPhones with Apple Intelligence, iOS 26 and later |
| Name | Weak. "The largest line" is often the brand, not the product | Better at the difference between brand and product. **Inferred**, not measured |
| Form | Good. Keywords: capsule, tablet, softgel, powder, drops, gummies, liquid | Good |
| Strength | Good. A pattern finds "500 mg", "1000 IU", "25 mcg" | Good, but it can return a number that is not on the label |
| Same result each time | Yes | No. It changes with the model version |
| Test without a device | Yes, in `MaruCore` with `swift test` | No. It needs a device with the model |
| Invented values | Not possible | Possible. A guard is necessary: accept a value only if the recognized text contains it |

The live scan of option 1 needs no parser for the name, because the user points at it. That is why option 1 comes first.

### 3.3 Barcode lookup

Checked with requests on 2026-10-11:

| Database | What it holds | Barcode lookup | Region | Terms and limits |
|---|---|---|---|---|
| [NIH DSLD](https://api.ods.od.nih.gov/dsld/v9) | 214,780 supplement labels. Name, brand, form, serving size, ingredients | Yes, with `search-filter` and the code in quotation marks. It needs the printed form with spaces, "8 17716 01789 1". The digits alone gave no result. 168 of 200 sampled labels had a code | United States | The API page states CC0 1.0. No key. I found no stated rate limit |
| [openFDA drug label](https://open.fda.gov/apis/authentication/) | 262,895 drug labels | 26,824 labels have a `upc` value, about 10% | United States | 1,000 requests each day for each IP address with no key. 120,000 each day with a key |
| [openFDA NDC](https://open.fda.gov/apis/authentication/) | 138,339 drug products. Name, form, strength, route | By NDC number, not by the retail barcode | United States | The same limits. The full file is about 27 MB zipped |
| [DailyMed](https://dailymed.nlm.nih.gov/dailymed/services/v2/spls.json) | Drug labels (SPL), from the same source as openFDA | By NDC number | United States | Free web service. I did not read its limits |
| [Open Food Facts](https://openfoodfacts.github.io/documentation/docs/Product-Opener/api/) | 32,314 products in the category "dietary supplements". Entered by volunteers | Yes | World, strongest in Europe | ODbL: attribution and share-alike. 15 product reads each minute for each IP address. A custom User-Agent is necessary |
| [UPCitemdb](https://www.upcitemdb.com/wp/docs/main/development/api-rate-limits/) | General retail products | Yes | Mostly the United States | Free plan: 100 requests each day for each IP address. "No guarantees on availability or accuracy" |

- Privacy cost: each lookup sends the product code from the user's IP address to a server. That tells the server which supplement or medicine the user has. `PRIVACY.md` says "It makes no network requests", and spec 10 says health data stays on the device. A network lookup breaks both. **Verified** (repository files).
- An offline copy of DSLD is realistic. Maru needs only the code, the name, the brand, and the form of each label. For about 215,000 labels that is an estimated 15 to 25 MB as text and 5 to 10 MB compressed. **Inferred.** I did not download the full database, and the download page blocked an automatic read.
- An offline copy of Open Food Facts is not realistic as a whole: the full file is 13.1 GB compressed, and the CSV file is 1.3 GB compressed. **Verified** (file sizes from the server). A filter to the supplement category gives a small file, but the ODbL share-alike rule then applies to the combined database, and the quality varies.
- A drug database for prescription medicines is out of scope (spec 13.1, and the gap study line 3).
- Coverage outside the United States is poor in every free source. **Inferred** from the table.

### 3.4 Speech

- System dictation: the name, amount, and note fields are standard SwiftUI text fields with the standard keyboard. The keyboard has a microphone key, so the add screen gets dictation today with no code. **Inferred** from `ItemEditorView.swift`. Nobody checked it on a device.
- Dictation can run on the device with no network for many languages. The app does not control this. **Inferred** from older Apple text. I could not open Apple's current page. See section 8.
- Speech framework, old API: `SFSpeechRecognizer` with `requiresOnDeviceRecognition = true` keeps the audio on the device, if `supportsOnDeviceRecognition` is true. Apple says that on-device results are less accurate. iOS 13 and later. **Verified** ([Apple docs](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition)).
- Speech framework, new API: `SpeechAnalyzer` with `SpeechTranscriber` is in iOS 26 and later. It can need a download of a language asset. `DictationTranscriber` uses the same models as system dictation, works on older devices, and accepts a list of words to prefer (`contextualStrings`). **Verified** ([SpeechAnalyzer](https://developer.apple.com/documentation/speech/speechanalyzer), [DictationTranscriber](https://developer.apple.com/documentation/speech/dictationtranscriber)).
- A speech feature in the app needs two more permissions: the microphone and speech recognition. **Inferred** from the Speech framework rules.
- App Intents: an app can give Siri and Shortcuts a set of phrases with `AppShortcutsProvider`. iOS 16 and later. Apple may extract the phrases and the titles of the intents to train its models. **Verified** ([Apple docs](https://developer.apple.com/documentation/appintents/appshortcutsprovider)).
- A spoken phrase works well with a parameter from a fixed list. Developers report that a parameter in a phrase often fails in Siri ([forum thread 713178](https://developer.apple.com/forums/thread/713178), [forum thread 759909](https://developer.apple.com/forums/thread/759909)). So "Add zinc every morning in Maru" in one sentence is not reliable. A phrase "Add an item in Maru", followed by Siri's question "What is the name?", is the form that works. **Inferred.**
- A natural sentence parser needs: the name, the days ("every day", "on weekdays"), and a time. "Every morning" is not a clock time. Maru can map it only to a time that the user already confirmed for a morning slot (spec 2.1), and it must show the plan for a confirmation. Without such a slot the item saves with no reminder. This is the hard part, and it gives little: the time wheel needs no typing today.

### 3.5 Other shortcuts

- Built-in list of names: about 150 to 300 common supplement names, written by hand and reviewed, for example "Vitamin D3", "Magnesium Glycinate", "Omega-3". The name field shows matches after the first letters. No network and no model. Spec 3 P02 already allows a search in "reviewed data". The list holds names only. It proposes no amount and no time.
- Paste: the text field accepts a paste today. **Inferred.**
- Apple Health import: an app can read the medications that the user allows, with a per-object permission sheet. It gets the name, the nickname, a general form, and if a schedule exists. It does not get the times. iOS 26 and later. **Verified** in `docs/research/2026-10-11-healthkit-medications-api.md`. It is useful only for a user who already keeps a list in Health. That user typed the names one time already. D022 keeps it as a later candidate.
- Duplicate: the replace flow (`ItemDraft.replacing`) already copies type, form, color, times, days, and note to a new item, with an empty name and amount. **Verified** (repository). A "Duplicate" action on an item is the same code with a different entry.
- Several items in one pass: spec 3 P03 already says "可继续加一项" after a save. A "Save and Scan Next" action gives a row of bottles in one session.

### 3.6 What competitors do

- Apple Health Medications: the camera add works only in the United States. "If you're in the United States, you can also use your iPhone camera to add a medication." The user taps the camera symbol, taps Next, and follows the steps. **Verified** ([Apple support 105064](https://support.apple.com/en-us/105064), published 2026-09-14). The camera reads the label and shows possible matches from Apple's drug list, and the user picks one. It needs an iPhone XR or later. **Inferred** from [Tom's Guide](https://www.tomsguide.com/how-to/how-to-set-up-medications-on-your-iphone) and older copies of Apple's page.
- So Apple's camera matches against a drug database of the United States. It does not help a user outside the United States, and it does not target supplements. A scan that works in every region is a point where Maru can be better. **Inferred.**
- MyTherapy: has a barcode scanner for medication packages. One reviewer could not get it to work, and a pharmacy sticker covered the barcode on some packages ([Parkinson's UK review](https://techguide.parkinsons.org.uk/catalogue/my-therapy/review)). Its App Store text does not name the scanner. The supported countries: not verified.
- Medisafe: I found no primary source for a scan feature. Medisafe is now a paid app for users outside the United States ([Medisafe help](https://help-center.medisafe.com/en/articles/13052285-medisafe-is-now-a-fully-paid-app-for-users-outside-the-u-s)).
- SuppCo: a barcode scanner against "a proprietary database over 160,000 supplements". It collects health data, name, email, and a user ID, linked to the identity of the user ([App Store](https://apps.apple.com/us/app/suppco-supplement-scanner/id6504838951)). **Verified.** Several small "AI supplement scanner" apps exist. One review says: "Can't scan a single supplement without paying for 12 weeks" ([Supp AI](https://apps.apple.com/us/app/supp-ai-supplement-scanner/id6749564990)).
- User feedback in this repository (`2026-10-11-user-feedback-cn.md`, theme 12): "If the scan reads it wrong and the user takes the wrong medicine, the fine can ruin you." "Add a confirmation step." One user asked if the label scan runs on the device (line 134). So users want the scan, they want a confirmation, and they ask about privacy. A scan on the device with a tap by the user answers all three.

### 3.7 Cloud vision models, as the comparison

Prices on 2026-10-11, in US dollars for one million tokens:

| Model | Input | Output | Source |
|---|---|---|---|
| Gemini 2.5 Flash-Lite | 0.10 | 0.40 | [Google](https://ai.google.dev/gemini-api/docs/pricing) |
| Gemini 3.8 Flash | 0.75 until 2026-12-31, then 1.50 | 3.75, then 7.50 | the same page |
| Claude Haiku 5.5 | 0.10 | 0.50 | [Anthropic](https://platform.claude.com/docs/en/about-claude/pricing) |
| Claude Sonnet 5.5 | 2.00 | 10.00 | the same page |
| OpenAI gpt-realtime-mini (image input) | 0.80 | 2.40 | [OpenAI](https://developers.openai.com/api/docs/pricing) |

- Cost of one scan, with my assumption of 1,500 input tokens for the photo and the prompt and 150 output tokens: about 0.0002 dollars with the cheapest models, about 0.0017 dollars with Gemini 3.8 Flash, and about 0.0045 dollars with Claude Sonnet 5.5. **Inferred.** The token count of one photo differs for each provider, and I did not measure it.
- For 10,000 scans that is 2 to 45 dollars. The price of a scan is not the problem.
- The real costs:
  1. A server. An API key must not ship inside the app, so Maru needs its own proxy server. Maru has no server (spec 1, `PRIVACY.md`). The owner then runs and pays a service, and must stop abuse of it.
  2. Privacy. The photo of a medicine label leaves the device. Google uses free-tier content to improve its products (the pricing page). A paid tier avoids that, but the photo still leaves the device.
  3. App Review. Guideline 5.1.2(i): "You must clearly disclose where personal data will be shared with third parties, including with third-party AI, and obtain explicit permission before doing so." **Verified** ([guidelines](https://developer.apple.com/app-store/review/guidelines/)). Maru then needs a consent screen, a new privacy label, and a new privacy policy.
  4. The startup and offline rules: the scan fails with no network.
- Accuracy gain: a large cloud model reads a busy or curved label better than a rule parser. **Inferred.** I found no independent measurement for supplement labels.
- Verdict: reject. The gain is a better proposal that the user still must check. The cost is the main promise of the product.

## 4. Recommended first version

Build option 1, the live label scan, with a keyword proposal for the form. It needs no model and no network. It works on every iPhone that Maru supports. The user makes each choice with a tap, so no value from a label is saved silently.

### The flow

Entry: the add button on Today or My Items opens the edit screen, as today. The name row gets a camera button, "Scan Label". A long press on the add button can open the scanner directly. That is a detail for the design.

1. **Camera permission.** The first tap on "Scan Label" asks for the camera (spec 2.2). If the user refuses, the edit screen stays and works as today.
2. **Scanner screen.** The camera opens in a sheet. The system highlights the text that it finds on the label. The top of the screen says: "Tap the name on the label." A "Cancel" button is at the top left.
3. **Tap 1: the name.** The user taps the product name. A card at the bottom shows "Name" and the text. The camera stays open. A tap on a different line replaces the name.
4. **Tap 2, optional: the amount.** The card has a second row, "Amount (Optional)", that is empty. The user can tap it and then tap a text on the label, for example "1000 IU". If the user does not, the amount stays empty.
5. **Last tap: "Use".** The sheet closes. The edit screen shows the name, and the amount if the user chose one. Both are ordinary text that the user can edit.
6. **Form proposal.** If the text that the scanner saw contains exactly one form word (capsule, tablet, softgel, powder, drops), the form row shows a button, for example "Use Softgel". The form menu itself does not change until the user taps the button. With no word or with two different words, nothing shows.
7. **Reminder and save.** The user adds a time with the wheel and taps "Save", as today. The scan sets no time, no days, and no note.

After the camera opens, the name needs two taps (the name, then "Use") and the name with an amount needs four. The scan saves all typing of the name.

For a row of bottles: after "Save", the notice offers "Scan Next", which opens a new draft with the scanner.

### What the user confirms

- The name: the user picked the line and sees it on the card and on the edit screen before the save.
- The amount: only if the user picked it. Maru never moves a number from the label to the amount by itself. A strength on a label is not the amount that the user takes (spec 2.1).
- The form: only after a tap on the proposal.
- The time: always by the user, with the wheel.

### An iPhone without the on-device model

The first version does not use the on-device model, so every iPhone has the same flow. The only device check is `DataScannerViewController.isSupported` and `isAvailable`. When the scanner is not available, for example when the user refused the camera, the "Scan Label" button does not show or it explains the camera setting, and the user types or dictates.

### Other parts of the first version

- No photo is stored. The scanner reads the live video, and Maru keeps only the text that the user tapped. This is simpler than the pipeline of spec 5.2.
- The form keyword check is a small pure function in `MaruCore`, so `swift test` covers it on the Mac.
- `project.yml` needs the camera usage text.
- Dictation needs no work. The FAQ can say that the microphone key of the keyboard fills the name.

## 5. The second step

In this order:

1. **Built-in list of supplement names (option 10).** Small. It helps when the bottle is not near the user, and on every iPhone. It needs a reviewed list and a decision on its source.
2. **One-shot proposal with the on-device model (options 3 and 4).** On an iPhone with Apple Intelligence, the scanner gets a shutter button. Maru reads all text of the frame and asks the model for name, form, and strength. The card shows the three proposals, and the user accepts each with a tap or corrects it. The guard: Maru shows a proposed value only if the recognized text contains it. On an iPhone without the model, the tap flow of the first version stays. On iOS 27 the model can take the photo directly, which can help with brand against product name. Build this only after a test of 20 real bottles shows that it is better than the tap flow.
3. **Duplicate an item (option 12).** Small.
4. **Barcode with an offline copy of NIH DSLD (option 6).** Only if users in the United States ask for it. It needs a check of the bulk download and its licence, an update process, and an entry in `docs/third-party-licenses.md`.
5. **"Add an item in Maru" for Siri and Shortcuts (option 9).** Siri asks for the name, and Maru opens the edit screen with the name filled. No schedule from speech.

## 6. Things to reject

| Thing | Reason |
|---|---|
| Cloud vision or language model (option 14) | The photo leaves the device. It needs a server, a consent screen, and a new privacy policy. The gain is only a better proposal |
| Apple's Private Cloud Compute model | It is a network request with a daily limit and a managed entitlement |
| Barcode lookup over the network (option 5) | Each lookup tells a server what the user takes. Coverage outside the United States is poor |
| An offline copy of Open Food Facts | The full file is 13.1 GB compressed. The share-alike licence applies to a combined database. The data quality varies |
| UPCitemdb | 100 requests each day for each IP address, no supplement detail, no accuracy promise |
| A drug name database for medicines | Out of scope (spec 13.1). United States data only |
| A microphone button and a sentence parser in the app (option 8) | Two more permissions and a large parser. System dictation already fills the name, and the time wheel needs no typing |
| A schedule from the label or from speech with no confirmed slot | Spec 2.1 forbids a default time. "Take one daily" on a label is not a clock time |
| The amount filled automatically from the strength on the label | Spec 2.1: no default amount. The strength of the product is not the amount that the user takes |
| Apple Health import now | iOS 26 only, a new HealthKit permission, and little value for supplement users. It stays on the later list (D022) |
| A photo of the leaflet to explain the medicine | Medical content. Users in the feedback study warned about responsibility for wrong data |

## 8. What I could not verify

- The quality of the live scanner on real supplement bottles: curved labels, glossy labels, small text, and vertical text. No code ran on a device. This is the main risk of the recommendation, and a test on the maintainer's iPhone with about 20 bottles answers it.
- The list of languages that the scanner and Vision recognize. The APIs return it at run time, and Apple's pages do not print it. The quality for Chinese labels is not known.
- How the scanner splits a label into items that the user can tap: by line or by block. A product name on two lines can need two taps or a different design.
- The quality of the on-device model for this task, and the token cost of one photo in iOS 27.
- The share of active iPhones with Apple Intelligence. Apple does not publish it.
- That every iPhone on iOS 17 has the A12 chip or later. I took it from memory of Apple's device list.
- If system dictation runs on the device for each language. I could not open Apple's current dictation page. The dictation of uncommon product names was not tested.
- The exact limits of parameters in App Shortcut phrases. I have forum reports, not Apple's rule text.
- The NIH DSLD bulk download: its size, its format, and its licence text. The API guide page blocked an automatic read. The CC0 statement is on the API page. The share of labels with a barcode comes from a sample of 200. The lookup of an EAN-13 code was not tested.
- The rate limit of the NIH DSLD API and of DailyMed.
- The countries of the MyTherapy barcode scanner, and if Medisafe has a scan.
- What Apple Health reads from a label, in Apple's own words. Apple's page gives only the region and the steps.
- The token count of one photo for each cloud provider, so the cost for each scan is an estimate. No accuracy number for cloud models on supplement labels exists in my sources.
- The effort values. They are estimates with no prototype behind them.
